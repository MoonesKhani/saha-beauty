# بررسی آمادگی OTP و اتصال رزرو — بدون ارسال یا انتشار

## پارامترهای لازم

API رمز یک‌بارمصرف فقط `to` (شماره نرمال‌شده همراه) می‌گیرد. کلید از محیط سرور
در مسیر HTTPS ثابت API قرار می‌گیرد؛ bodyId، فرستنده یا args برای این روش لازم نیست.
کد تولیدشده ملی پیامک فقط به بک‌اند می‌رسد؛ HMAC آن با انقضای ۱۲۰ ثانیه ذخیره می‌شود.
به تنظیمات فعلی خط/کلید ملی پیامک در سرور دست زده نشده است. تنظیمات ارسال الگویی
مستقل و غیرفعال مانده‌اند و فعال‌سازی OTP به آن‌ها وابسته نیست.

برای اجرای بک‌اند، کلید API و secret مستقل باید به محیط **کانتینر app** برسند؛
ثبت موفق در فایل `.env` به‌تنهایی بارگذاری در فرایند قبلی یا نصب مسیرها را ثابت نمی‌کند.
پرچم‌های ارسال تا تأیید مالک خاموش‌اند؛ خاموش‌بودن، علت ۴۰۴ نیست. در نسخه نصب‌شدهٔ
جدید، مسیر درخواست OTP وقتی غیرفعال است ۵۰۳ می‌دهد، نه ۴۰۴.

## اتصال رزرو

- قبل از این اصلاح، ورود فقط یک لینک اختیاری بود و رزرو عمومی تأیید شماره نمی‌خواست.
- `SAHA_BOOKING_REQUIRE_OTP=0` پیش‌فرض است و رزرو موجود حفظ می‌شود.
- در راه‌اندازی تأییدشده، مقدار ۱ باعث الزام نشست معتبر و یکسان‌بودن شماره رزرو
  و شماره تأییدشده می‌شود؛ برای رزرو تکی و چندمتخصصی، در خود سرور اجرا می‌شود.
- صفحه رزرو، عروس یا تولد در حالت اجباری کاربر مهمان را به ورود می‌فرستد؛ پس از
  ورود به همان مسیر و query اولیه بازمی‌گردد. مقصد خارجی برای بازگشت پذیرفته نمی‌شود.
- شماره تأییدشده در همان فیلد قبلی قرار می‌گیرد؛ CSS و چیدمان HTML عوض نشده‌اند.
- ارسال فرم دوباره نشست را بررسی می‌کند؛ منقضی‌شدن نشست هرگز اجازهٔ رزرو بدون تأیید نمی‌دهد.
  انتخاب ساعت پس از ورود همچنان با موجودی واقعی سرور بررسی می‌شود؛ رزرو خودکار انجام نمی‌شود.

## مسیریابی و رفع ۴۰۴

FastAPI مسیرهای `/api/v1/auth/*` را ثبت می‌کند؛ صفحه ورود نیز در build موجود است.
مستندات OpenAPI از `/api/openapi.json` ارائه می‌شوند تا پشت پراکسی `/api/` به
مسیر اشتباه ریشهٔ Pages نروند. `deploy/Caddyfile` از قبل مسیرها را کامل به
`app:8000` می‌فرستاد؛ همان upstream حفظ شده و کش API از جمله خطاهای ۴۰۴ ممنوع شده است.

تنظیم موجود **واقعی** origin/CDN باید قبل از اعمال خوانده شود؛ اگر Caddy موجود
نیست نباید آن را از صفر جایگزین وب‌سرور فعلی کرد. در همان پراکسی فعلی باید:

1. تمام `/api/*` با prefix کامل و Host/HTTPS صحیح به app فعلی بروند؛ هیچ
   `handle_path` یا rewrite نباید `/api` را حذف کند.
2. کش CDN/پراکسی برای API خاموش باشد؛ صفحه `login.html` و assets از همان بسته
   بازبینی‌شده منتشر شوند و کوکی نشست روی همان دامنه بماند.
3. پاسخ origin داخل سرور و پاسخ دامنه با هم مقایسه شوند تا نصب‌نشدن نسخه از
   اشتباه route دامنه تفکیک شود. اتصال Codex به فرمان عمومی SSH فعلاً در دسترس نیست.

بررسی عمومی فعلی: capabilities و OpenAPI جدید روی دامنه ۴۰۴ می‌دهند؛ بنابراین
کد آماده‌شده هنوز از مسیر عمومی قابل استفاده نیست. در یک بررسی، health پاسخ نداد؛
این خطای شبکه تأیید خرابی دیتابیس نیست. ابزار زیر فقط چهار GET بدون کلید می‌زند:

```bash
python3 scripts/check-otp-http.py
```

این ابزار شماره، OTP، کلید، پاسخ خام یا هدر محرمانه چاپ نمی‌کند و هیچ POST ندارد.
`ready_for_activation_review` فقط آمادگی مسیرها و دیتابیس را نشان می‌دهد؛ تأیید
اعتبار واقعی کلید یا ارسال/تحویل پیامک نیست. timeout به‌صورت نامشخص گزارش می‌شود.

## مراحل باقی‌مانده برای راه‌اندازی واقعی — فقط پس از تأیید مالک

1. رفع مانع انتقال انتشار با آزمون کوتاه، بدون تکرار کور انتقال طولانی.
2. نهایی‌کردن طرح maintenance مربوط به `0004_packages → 0005_auth_sms`، بکاپ و
   آزمون آن، و image بازیابی سازگار با schema جدید. guard فعلی عوض نشده است و
   انتشار عادی این تغییر schema را متوقف می‌کند؛ دورزدن آن مجاز نیست.
3. نصب نسخه بازبینی‌شده، بارگذاری متغیرهای موجود در app و بررسی پراکسی فعلی با
   ارسال همچنان خاموش. بدون تغییر طراحی، تعرفه، رزرو، uploads یا کلیدهای قبلی.
4. اجرای GETهای آمادگی؛ سپس فقط با تأیید جداگانه، یک تست واقعی به شماره انتخابی
   مالک و تأیید کد. فعال‌کردن عمومی ارسال/الزام ورود نیز تصمیم جداگانه است.

در این مرحله هیچ migration تولیدی، تغییر تنظیمات زنده، ارسال پیامک یا انتشار انجام نشده است.
