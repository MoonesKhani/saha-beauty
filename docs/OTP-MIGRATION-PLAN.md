# طرح maintenance مستقل OTP؛ هنوز مجوز اجرا نیست

## حدود کار

مقصد schema فقط `0005_auth_sms` و مبدأ فقط `0004_packages` است. migration پنج
جدول جدید مشتری، چالش، نشست، محدودیت و صف می‌سازد و جدول قدیمی را بازنویسی نمی‌کند.
`server-update.sh --release` همچنان فقط schema برابر را می‌پذیرد؛ این طرح مسیر
نگه‌داری جداگانه است و نباید برای عبور از guard انتشار عادی استفاده شود.

هیچ دستور این سند در سرور اجرا نشده است. ارسال، الزام ورود و timer پیامک تا تأیید
جداگانه خاموش می‌مانند. تغییر OTP در main به‌تنهایی هیچ سایتی را منتشر نمی‌کند.

## پیش‌شرط‌های لازم برای تأیید نهایی

- commit کامل اصلی، CI موفق و checksum بستهٔ دریافت‌شده مشخص باشد.
- آزمون کوتاه اتصال و انتقال موفق باشد؛ اگر توان انتقال برای بسته کافی نیست،
  انتقال کامل تکرار نشود و مسیر جایگزین امن بررسی شود.
- بازرسی همان Compose پروژه موجود: app یکتا، پورت و uploads volume بدون تغییر،
  db سالم و revision دقیق 0004. تغییرات دستی ناشناخته یا env ناسازگار باعث توقف است.
- تمام پرچم‌های live/OTP/notifications/booking-require-OTP صفر بمانند. کلید و secret
  ثبت‌شده فقط روی سرور حفظ و از .env به app بارگذاری شوند؛ هیچ مقداری چاپ نشود.
- قبل از اجرا **image بازیابی با head=0005 و سلامت روی هر دو schema 0004 و 0005**
  باید در GitHub ساخته و در محیط موقت آزمایش شده باشد. image قدیمی با readiness
  فقط 0004 برای بعد از migration کافی نیست؛ بدون این image اجرا ممنوع است.

## ترتیب تراکنش پیشنهادی

1. دریافت کامل و بررسی اندازه/SHA-256 بسته؛ بررسی image ID و label نسخه و schema؛
   image اصلی و بازیابی با docker load محلی، بدون build یا pull روی آروان.
2. قفل انتشار، کنترل فضای خالی و ثبت image/mount/config فعلی. از DB با pg_dump،
   uploads و .env و Compose پشتیبان خصوصی گرفته شود؛ pg_restore --list، فهرست tar
   و checksumها باید تأیید شوند. دادهٔ زنده از بکاپ جایگزین نمی‌شود.
3. image بازیابی/پل با ارسال خاموش و همان پورت/volume اجرا شود؛ روی schema 0004
   باید سلامت و APIهای خدمات/قیمت/رزرو را بگذراند. شکست در این مرحله بازگشت به
   image اصلی 0004 است و هنوز migration انجام نمی‌شود.
4. migration افزایشی به 0005 با image بازبینی‌شده و PostgreSQL تراکنشی اجرا شود؛
   نسخه و وجود جدول‌ها بررسی شوند؛ داده‌ها و فایل‌های بعد از بکاپ نیز باقی بمانند.
5. سلامت همان image بازیابی روی schema 0005 بررسی شود. اکنون آن image مقصد
   rollback سازگار است؛ DB به 0004 downgrade یا از dump restore نشود.
6. نسخه اصلی از مسیر **عادی** server-update نصب شود: head قبلی/بعدی/DB همه 0005
   و guard بدون استثنا برقرار است. نصب app، سلامت، APIهای OTP با ارسال خاموش و
   انتشار فایل‌های ثابت فقط با مجوز نهایی همان نسخه انجام شوند.
7. معیار اتمام: GET health و capabilities و OpenAPI صحیح، ورودی رزرو درست،
   volume/config و سوابق حفظ‌شده، ارسال خاموش. سپس برای یک تست واقعی و فعال‌سازی
   عمومی از مالک تأیید جدا گرفته شود.

## شکست و بازیابی

قبل از migration، image اصلی 0004 قابل بازگشت است. بعد از migration فقط image
سازگار 0005 مجاز است. شکست یا قطع پردازش بعد از ارسال خارجی نامشخص، اجرای مجدد
کور ایجاد نمی‌کند؛ ابتدا state و سلامت فقط‌خواندنی بررسی می‌شوند. restore/downgrade
DB، حذف volume، reset/clean مخزن یا جایگزینی uploads هیچ‌کدام بخشی از این طرح نیست.
اگر recovery در حالت الزام OTP نتواند احراز هویت کند، رزرو عمومی باید fail-closed
شود و هماهنگی تلفنی باقی بماند؛ rollback نباید تأیید شماره را بی‌صدا حذف کند.

## آزمون‌ها و وضعیت

تست افزایشی SQLite و تست‌های PostgreSQL روی DBهای موقت، حفظ رزرو و قیمت و مصرف
یک‌باره OTP را بررسی کرده‌اند. CI کانتینری عادی نیز بکاپ، image rollback و حفظ
رزرو/آپلود/env را پوشش می‌دهد. ساخت و تمرین image پل دو-schema، همراه نتیجه
آزمون کوتاه شبکه، قبل از درخواست مجوز maintenance باید به این طرح ضمیمه شود.

## پیاده‌سازی مسیر جداگانه

- `prepare_otp_recovery.py` سورس قدیمی دقیق
  `cddc860800bf654af5f4483c32f8de646a598536` را به‌عنوان یک لایه کوچک روی image
  جدید می‌گذارد؛ readiness هر دو schema را می‌پذیرد، migration 0005 را دارد و
  هنگام الزام OTP، رزرو ناشناس را مسدود می‌کند. ساخت فقط روی GitHub است.
- بسته هر دو image و ID/label/schema آن‌ها را دارد؛ لایه‌های مشترک یک بار ذخیره
  می‌شوند. `deploy_otp_migration.py` فقط با مجوز جداگانه و قفل موجود اجرا می‌شود.
- overlay خصوصی `.deploy/compose.otp-env.json` فقط ارجاع متغیرها را دارد، نه
  مقدار کلید؛ ارسال واقعی، OTP، notifications و الزام OTP را صفر نگه می‌دارد.
  این overlay در تنظیمات Compose باقی می‌ماند. فعال‌سازی بعدی به تغییر صریح و
  تأییدشده همین پرچم‌ها نیاز دارد؛ تغییر `.env` به‌تنهایی آن‌ها را روشن نمی‌کند.
- پس از backup، پل روی 0004 اجرا، migration تراکنشی اعمال و پل روی 0005 آزموده
  می‌شود؛ سپس تابع انتشار عادی با guard برابر اجرا می‌شود. شکست image جدید،
  نسخه پل 0005 را نگه می‌دارد و داده‌ها از backup جایگزین نمی‌شوند.
- retry فقط برای همان commit ثبت‌شده و schema تأییدشده مجاز است؛ خطای وضعیت
  نامشخص یا rollback_failed مانع ادامه می‌شود.
- CI در `otp_migration_container_test.py` روی volumeهای UUID موقت، سلامت هر دو
  schema، شکست آزمایشی بررسی سلامت image جدید، بازیابی پل، حفظ داده نوشته‌شده
  بعد از backup، uploads و env، و ادامه امن همان نسخه را بررسی می‌کند.

اجرای production، انتشار Pages و ارسال پیامک هیچ‌کدام در این آماده‌سازی انجام
نمی‌شوند. ابتدا ارتقای helper و آزمون کوچک HTTPS آروان؛ سپس معرفی SHA اصلی و CI
موفق به مالک و دریافت تأیید نهایی migration/انتشار لازم است.

## سازگاری افزودن تنظیمات OTP به کانتینر قدیمی

تشخیص سرور برای تلاش تأییدشدهٔ f1defac: فهرست changed در app خالی و تمام تفاوت‌ها
فقط تنظیمات OTP/SMS جدید از ENVIRONMENT بودند؛ db هیچ تفاوتی نداشت. تلاش قبل
از backup، تغییر کانتینر یا migration متوقف شد و بستهٔ کامل با checksum درست
در گیرنده باقی مانده است.

فقط MaintenanceEngine در همین مسیر جداگانه، تنظیمات فهرست‌شده در ENVIRONMENT
را در صورتی می‌پذیرد که در کانتینر و پیش‌فرض image قدیمی وجود نداشته باشند.
پرچم‌های جدید ارسال/OTP/اعلان/الزام ورود باید صفر باشند. تغییر مقدار یک کلید
موجود (حتی OTP)، افزودن کلید ناشناخته یا تفاوت db همچنان رد می‌شود. ComposeEngine
انتشار و rollback عادی همچنان کاملاً strict است؛ schema guard تغییری ندارد.

پذیرفتن افزودن تنظیمات در preflight چیزی را روی سرور فعال نمی‌کند. ابتدا همان
backup و کنترل schema اجرا می‌شود، سپس overlay بررسی‌شدهٔ خاموش، تنظیمات جدید
را بارگذاری می‌کند. این edge case در تمرین Docker با کانتینر legacy فاقد OTP و
Compose جدید بازسازی می‌شود؛ تست ردکردن آن در انتشار عادی نیز برقرار است.

برای ادامهٔ همان انتشار تأییدشده، artifact و CI و revision دقیق f1defac تغییر
نمی‌کنند؛ فقط ابزار نصب پس از CI موفق اصلاح می‌شود. ابزار انتقال قبل از آپلود،
وجود همان بسته با اندازه و SHA-256 دقیق را از گیرنده می‌پرسد و در صورت صحت از
آن استفاده می‌کند. هیچ unit ناموفق قبلی reset/حذف یا نصب نامشخص کور تکرار نمی‌شود.

## تفاوت شناسهٔ Docker classic و containerd

در تلاش بعدیِ همان نسخهٔ تأییدشده، بارگذاری image موفق شد اما مقایسهٔ شناسه متوقف
شد. بررسی مستقیم artifact اصلی با کنترل SHA-256 ZIP و release.tar نشان داد:

- شناسهٔ ثبت‌شدهٔ primary در manifest انتشار، digest پیکربندی `eb6fa2c8…` است؛
  Docker 29.1.3 سرور digest همان OCI manifest یعنی `e0e48a72…` را گزارش می‌کند.
- برای recovery نیز config برابر `7b7d2f99…` و manifest برابر `c1d2415d…` است.
- هر دو زوج در همان image.tar.gz تأییدشده موجودند و descriptor محتوا به config
  دقیق اشاره می‌کند. برچسب نسخه و role هر دو نیز مطابق بسته است. این تفاوتِ روش
  نمایش شناسه در image store است، نه مجوز نادیده‌گرفتن خطای صحت فایل.

`image_identity.py` فقط از metadata دارای digest معتبر و محدودیت حجم، در همان
بستهٔ قبلاً تأییدشده، رابطهٔ config/manifest/index را اثبات می‌کند. platform باید
linux/amd64 باشد؛ RootFS، تنظیمات اجرایی و revision باید دقیقاً مطابق config باشند.
برچسب revision به‌تنهایی کافی نیست. digest نامرتبط، تغییر Cmd/Env/User یا layer و
descriptor دستکاری‌شده همچنان رد می‌شوند.

شناسهٔ اصلی artifact در state، خروجی Workflow و release.json حفظ می‌شود؛ فقط
`runtime_image_id` اثبات‌شده برای فرمان Docker ذخیره می‌شود. این mapping در rollback،
بازیابی سازگار و استخراج سایت نیز استفاده می‌شود. مقدار runtime دریافتی از artifact
نادیده گرفته و روی همان میزبان دوباره اثبات می‌شود. بسته و image تأییدشدهٔ f1defac
بازنویسی یا rebuild نمی‌شوند. Docker یا image store سرور نیز تغییر نمی‌کند.

اگر هر دو image از قبل دقیقاً موجود و اثبات‌شده باشند، load تکراری انجام نمی‌شود.
در صورت نبودن/ناسازگاری، همان archive تأییدشده با کنترل فضای لازم load و دوباره
بررسی می‌شود. کنترل فضای backup و حفظ volumeها مستقل و بدون تغییر باقی می‌مانند.

برای خطاهای بعدی، فقط stage و operation ثابتِ خود ابزار در last-failure.json خصوصی
ثبت می‌شوند؛ exception/stderr/.env یا journal خام ذخیره و بازگردانده نمی‌شود. گیرنده
فقط در صورت تطبیق commit و InvocationID همان unit ناموفق این اطلاعات را می‌دهد.
